Рівень 1. Архітектурні патерни

Ласкаво просимо до Модуля 5 "Architecture & Logic". Ви вже пройшли великий шлях: від синтаксису Python до створення складних асинхронних API та роботи з Docker. Тепер настає переломний момент. До цього ви вчилися писати код, який працює. Тепер ми будемо вчитися писати код, який живе довго.

Ми розберемо, як проєктувати додатки так, щоб їх можна було підтримувати та масштабувати. Ми вивчимо класичні патерни проєктування, але — і це критично важливо — ми подивимося на них крізь призму Python. Ви дізнаєтеся, чому деякі рішення з підручників по Java виглядають у Python зайвими, і навчитеся писати ідіоматичний, чистий код.

Що таке патерни проєктування

У програмуванні, як і в будівництві, є типові проблеми. Як створити об'єкт, якщо ми не знаємо його тип заздалегідь? Як подружити два класи, які розмовляють різними мовами?

Design Pattern — це перевірене часом, стандартне рішення поширеної архітектурної задачі. Це не готовий код, який можна скопіювати, а скоріше шаблон або схема вирішення проблеми.

Навіщо вивчати патерни, якщо задачу можна вирішити інтуїтивно?

  1. Патерни формують мову спілкування всередині команди. Фраза "Використовуй тут Стратегію" замінює години пояснень структури класів.
  2. Це квінтесенція досвіду індустрії. Використання патернів захищає від винайдення велосипедів та типових архітектурних помилок.
  3. Знання патернів допомагає бачити структуру програми цілком, абстрагуючись від деталей реалізації.

Історичний контекст: Звідки вони взялися?

Фундаментальна праця в цій галузі — книга "Design Patterns", що вийшла у 1994 році. Її авторів називають "Band of Four" (GoF) — Банда Чотирьох.

Важливо розуміти контекст: Книга була написана на основі досвіду C++ та Smalltalk.

  • У C++ тих років не було автоматичного управління пам'яттю.
  • Не було модулів (як у Python).
  • Була жорстка статична типізація.

Багато патернів (наприклад, Singleton або Factory) у книзі GoF вирішують проблеми, яких у сучасному Python просто не існує або вони вирішуються засобами самої мови.

Рекомендуємо відвідати - https://refactoring.guru/

"Карго-культ" у Python

Поширена помилка при переході до архітектури — сліпе копіювання патернів із Java або C++ у Python. Це призводить до надмірного ускладнення.

Простий скрипт не повинен перетворюватися на ієрархію з десяти класів та п'яти інтерфейсів тільки заради відповідності "книжковому" визначенню патерна. Код на Python повинен залишатися читабельним та лаконічним.

Наш підхід до вивчення:

  1. Academic/Classic: як патерн описується в теорії (важливо для розуміння суті та проходження співбесід).
  2. The Pythonic Way: як цей патерн реалізується в ідіоматичному Python, використовуючи можливості мови.

UML для розробника

Патерни — це про зв'язки між об'єктами. Щоб не малювати код на дошці, використовують UML (Unified Modeling Language). Вам не потрібно знати його ідеально, достатньо розуміти основні стрілки.

Основні типи відносин

classDiagram class Car { +Engine engine +start() } class Engine { +work() } class Driver { +drive() } class Wheel { +rotate() } Car *-- Engine : Композиція (Composition) Частина вмирає без Цілого Car o-- Wheel : Агрегація (Aggregation) Частина може жити окремо Driver ..> Car : Залежність (Dependency) Driver використовує Car
  • Композиція: жорсткий зв'язок. Двигун — частина Машини. Немає машини — немає двигуна.
  • Агрегація: м'який зв'язок. Колесо — частина Машини, але його можна зняти та покласти в гараж.
  • Залежність: один об'єкт тимчасово використовує інший (наприклад, у параметрах методу).

Група 1: Породжувальні патерни (Creational)

Ця група патернів відповідає за створення об'єктів. Здавалося б, що може бути простішим за виклик MyClass()?

Але проблеми виникають, коли:

  • Ми не знаємо заздалегідь, який клас нам знадобиться.
  • Нам потрібно гарантувати, що об'єкт лише один.
  • Ініціалізація об'єкта занадто складна і вимагає безлічі кроків.

Singleton (Одинак)

Гарантує, що у класу є тільки один екземпляр, і надає до нього глобальну точку доступу.

classDiagram class Singleton { -static instance -Singleton() +static getInstance() }

Academic Approach

Використання методу __new__ для контролю створення об'єкта.

class Singleton:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

# s1 і s2 - це один і той самий об'єкт
s1 = Singleton()
s2 = Singleton()

The Pythonic Way (Як робимо ми)

У Python модуль — це вже Singleton. Він імпортується один раз, і всі наступні імпорти повертають посилання на той самий об'єкт модуля.

# db_config.py
print("Connecting to DB...")
connection = DatabaseConnection(url="...")

# main.py
from db_config import connection
# Просто використовуємо об'єкт connection. Він гарантовано один.

Builder (Будівельник)

Відокремлює конструювання складного об'єкта від його представлення. Дозволяє створювати об'єкт покроково.

graph LR Client --> Builder Builder -- 1. setPartA --> Object Builder -- 2. setPartB --> Object Builder -- 3. getResult --> Client

Коли це Overengineering?

Якщо ви робите Builder просто, щоб уникнути довгого конструктора:

# Погано в Python (Java-style)
car = CarBuilder().set_color("Red").set_engine("V8").build()

The Pythonic Way

Використовуйте іменовані аргументи в __init__.

# Добре
car = Car(color="Red", engine="V8", wheels=4)

Коли Builder реально потрібен?

Коли створення об'єкта вимагає складної логіки, різних етапів або перетворень даних (наприклад, ORM або побудова звітів).

# SQLAlchemy Query Builder - чудовий приклад
query = session.query(User).filter(User.age > 18).order_by(User.name)
# Ми "будуємо" SQL-запит по кроках

Factory Method (Фабричний метод)

Визначає інтерфейс для створення об'єкта, але залишає підкласам рішення про те, який клас інстанціювати.

classDiagram class Creator { +createProduct() } class ConcreteCreatorA class ConcreteCreatorB Creator <|-- ConcreteCreatorA Creator <|-- ConcreteCreatorB ConcreteCreatorA ..> ProductA : Creates ConcreteCreatorB ..> ProductB : Creates

Проблема

Вам потрібно парсити дані, але формат (JSON, XML, YAML) стає відомим тільки в момент отримання файлу.

The Pythonic Way

Замість створення складної ієрархії класів Creator та ConcreteCreator, у Python часто використовують словник диспетчеризації або функції-фабрики.

def get_parser(format_type: str):
    parsers = {
        'json': JsonParser,
        'xml': XmlParser,
        'yaml': YamlParser
    }
    # Повертаємо клас або функцію, не створюючи об'єкт одразу
    return parsers.get(format_type, DefaultParser)()

# Використання
parser = get_parser('json')
parser.parse(data)

Abstract Factory (Абстрактна фабрика)

Дозволяє створювати сімейства пов'язаних об'єктів (без прив'язки до конкретних класів). Це "Фабрика фабрик".

classDiagram class GUIFactory { +createButton() +createWindow() } class WinFactory class MacFactory GUIFactory <|-- WinFactory GUIFactory <|-- MacFactory WinFactory ..> WinButton : Creates WinFactory ..> WinWindow : Creates

Приклад із життя

Уявіть, що ви пишете UI-бібліотеку, яка повинна працювати і на Windows, і на macOS.

  • Якщо ОС Windows -> потрібні кнопки WinButton та вікна WinWindow.
  • Якщо ОС macOS -> потрібні MacButton та MacWindow.
  • Не можна змішувати WinButton з MacWindow.

Абстрактна фабрика гарантує, що всі створювані об'єкти належатимуть до однієї "теми" або "платформи". У веб-розробці зустрічається рідше, наприклад, при виборі драйвера бази даних (PostgresFactory vs MySQLFactory), що створює сумісні з'єднання та курсори.

Prototype (Прототип)

Створення нових об'єктів шляхом клонування вже існуючих (прототипів).

graph LR Default[Default Config] -- "1. copy.deepcopy()" --> UserConf[User Config] UserConf -- "2. Change Settings" --> UserConfMod["User Config (Theme: Dark)"] Default -. "Remains Unchanged" .-> Default style UserConf stroke-dasharray: 5 5

Навіщо? Створення об'єкта з нуля може бути дорогим (запити в БД, складні обчислення), а копія робиться швидко.

Python Implementation

У Python цей патерн реалізований у стандартній бібліотеці copy.

import copy

class Config:
    def __init__(self):
        self.settings = self._load_heavy_settings_from_db() # Довго!

# Створюємо один раз
default_config = Config()

# Клонуємо для кожного користувача
user_config = copy.deepcopy(default_config)
user_config.settings['theme'] = 'dark'

Група 2: Структурні патерни (Structural)

Ми створили об'єкти. Тепер їх потрібно зв'язати в працюючу систему. Структурні патерни відповідають за композицію класів та об'єктів.

Основні завдання:

  • Поєднати несумісне (Adapter).
  • Спростити складне (Facade).
  • Додати функціонал без успадкування (Decorator).

Adapter (Адаптер)

Дозволяє об'єктам із несумісними інтерфейсами працювати разом. Діє як "перехідник".

classDiagram class Client class Adapter { +request() } class OldSystem { +specific_request() } Client --> Adapter : uses standard interface Adapter --> OldSystem : calls specific method

The Pythonic Way: Duck Typing

У статичних мовах адаптер зобов'язаний реалізовувати конкретний Інтерфейс. У Python працює Duck Typing: "Якщо це ходить як качка і крякає як качка, то це качка".

class OldLogger:
    def log_message(self, msg): ...

class NewSystem:
    def log(self, text): ...

# Adapter
class LoggerAdapter:
    def __init__(self, old_logger):
        self.old_logger = old_logger

    def log(self, text):
        # Адаптуємо виклик
        self.old_logger.log_message(text)

Нам не потрібно успадковувати LoggerAdapter від якогось базового класу, головне, щоб у нього був метод log.

Decorator (Декоратор)

Не плутайте патерн проєктування "Декоратор" та синтаксис декораторів Python (@wrapper). Хоча вони вирішують схожі завдання.

graph LR Client --> Wrapper[Decorator] Wrapper -- "Extra Logic" --> RealObject

Суть патерна: Динамічне додавання об'єкту нових обов'язків. Гнучка альтернатива успадкуванню.

Візуалізація

graph LR Client --> Decorator Decorator -- "дод. логіка" --> Component

Приклад

У вас є об'єкт Response. Ви хочете огорнути його в GzipDecorator, щоб стиснути дані, а потім у LogDecorator, щоб залогувати відправлення. У Python це часто реалізується через Middleware (наприклад, у Django або FastAPI) або дійсно через синтаксис @.

Facade (Фасад)

Надає простий інтерфейс до складної системи класів, бібліотеки або фреймворку.

classDiagram class Client class Facade { +simple_operation() } class SubsystemA class SubsystemB class SubsystemC Client --> Facade Facade --> SubsystemA Facade --> SubsystemB Facade --> SubsystemC

Проблема

У вас є бібліотека для роботи з відео, де потрібно ініціалізувати Codec, BitrateManager, AudioMixer, Buffer...

Рішення

Ви створюєте один клас VideoConverter з одним методом convert(file, format).

Приклад із Python

Бібліотека requests — це чудовий Фасад. Всередині неї складна робота з urllib3, сокетами, пулами з'єднань, кодуваннями. Але для вас це просто:

requests.get('https://google.com')

Ви не бачите складності, прихованої за фасадом.

Proxy (Замісник)

Об'єкт, який контролює доступ до іншого об'єкта.

classDiagram class Client class Proxy { +request() } class RealSubject { +request() } Client --> Proxy Proxy --> RealSubject : Forwards request if allowed/needed

Види Proxy:

  1. Lazy Proxy (Лінивий/Віртуальний): створює важкий об'єкт тільки тоді, коли він реально потрібен.
  2. Remote Proxy (Віддалений): локальний представник об'єкта, який знаходиться на іншому сервері.
  3. Protection Proxy (Захисний): перевіряє права доступу при зверненні до об'єкта.

Приклад: Django Lazy Objects

У Django, коли ви звертаєтеся до request.user всередині view, запит до бази даних не відбувається одразу. Django створює Proxy-об'єкт. Реальний SQL-запит виконається тільки тоді, коли ви спробуєте прочитати поле, наприклад request.user.username.

Bridge та Composite

Два патерни, які варто розуміти концептуально.

Bridge (Міст)

Розділяє абстракцію та реалізацію так, щоб вони могли змінюватися незалежно. Приклад: Абстракція "Геометрична Фігура" (Коло, Квадрат) відокремлена від Реалізації "Малювання" (на Екрані в Пікселях або на Принтері у Векторах).

classDiagram class Shape { +draw() } class DrawingAPI { +draw_circle() } Shape o-- DrawingAPI : Bridge class Circle class Square Shape <|-- Circle Shape <|-- Square class VectorAPI class RasterAPI DrawingAPI <|-- VectorAPI DrawingAPI <|-- RasterAPI

Це дозволяє додати нову фігуру (Triangle) без зміни API малювання, і додати новий API (SVG) без зміни фігур.

Composite (Компонувальник)

Дозволяє згрупувати об'єкти в деревоподібну структуру і працювати з групою так само, як з одиничним об'єктом. Приклад: Графічний інтерфейс. Window містить Panel, яка містить Button та TextField. Ви викликаєте Window.draw(), і воно рекурсивно викликає draw() у всіх дітей.

graph TD Menu --> File Menu --> Edit File --> New File --> Open Edit --> Copy Edit --> Paste

Клієнт викликає метод draw() у кореня (Menu), і команда рекурсивно проходить по всіх елементах дерева.

Підсумки

Не намагайтеся запхати патерни скрізь, де це можливо. Це називається Overengineering.

  1. Спочатку пишіть простий, зрозумілий код.
  2. Якщо відчуваєте біль (дублювання, складність модифікації) — подивіться, який патерн вирішує цю проблему.
  3. Використовуйте можливості Python (модулі, декоратори, ітератори) перед тим, як будувати складні класові структури в стилі Java.
