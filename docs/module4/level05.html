Рівень 5: Тестування FastAPI-застосунків з Pytest

Непротестований код — це код, який не працює. Забезпечення коректності та надійності вашого API є критично важливим. Ми освоїмо тестування FastAPI-застосунків, використовуючи pytest — де-факто стандарт для тестування у Python.

Ви дізнаєтеся, як TestClient дозволяє надсилати HTTP-запити до вашої аплікації без запуску реального веб-сервера, а фікстури pytest спростять підготовку тестових даних та об'єктів. Ми навчимося писати тести для різних HTTP-методів, перевіряти коректність обробки помилок, мокувати зовнішні API для ізоляції тестів, а також тестувати захищені ендпоінти з JWT.

Завершимо вивченням pytest-cov для аналізу покриття коду, що дозволить вам підтримувати високу якість API.

Інструменти для тестування FastAPI

Для тестування FastAPI-застосунків ми використовуватимемо стандартний набір інструментів з екосистеми Python.

  • pytest: де-факто стандарт для тестування в Python. Надає простий синтаксис на основі assert, потужну систему фікстур та плагінів.

  • TestClient: спеціальний клас, що надається FastAPI, для надсилання HTTP-запитів до вашого застосунку безпосередньо, без запуску реального вебсервера. Він працює на базі бібліотеки httpx.

  • імпорт: from fastapi.testclient import TestClient
  • httpx: сучасна асинхронна бібліотека для HTTP-запитів. TestClient використовує її "під капотом".
  • pytest-cov: плагін для pytest для вимірювання та аналізу покриття коду тестами.

Організація тестів у проєкті

Рекомендовано зберігати тести в окремій директорії tests/ у корені вашого проєкту.

Приклад структури:

my_fastapi_project/
├── app/
│   ├── __init__.py
│   └── main.py       # Ваш код FastAPI
├── tests/
│   ├── __init__.py
│   └── test_main.py  # Файл з тестами для main.py
├── .env
├── pytest.ini        # Файл налаштувань pytest
└── requirements.txt

Файл pytest.ini допомагає pytest знайти ваші тести та налаштувати його поведінку.

[pytest]
# Опції для запуску, наприклад, -v (verbose)
addopts = -v
# Вказуємо, де шукати тести
testpaths = tests

Файл з тестами (tests/test_main.py): імена файлів тестів повинні починатися з test_, а тестових функцій — також з test_.

TestClient та фікстури Pytest

TestClient імітує надсилання запитів до вашого FastAPI-застосунку. Його прийнято створювати один раз і перевикористовувати в тестах. Найкращий спосіб для цього — фікстура pytest.

Фікстури (@pytest.fixture) готують дані або об'єкти для тестів.

Приклад фікстури для TestClient та даних (можна розмістити у tests/conftest.py або в файлі з тестами):

import pytest
from fastapi.testclient import TestClient
from app.main import app # Імпортуємо наш FastAPI-застосунок

@pytest.fixture(scope="module") # scope="module" — фікстура створиться один раз для всіх тестів у модулі
def client():
    """ Фікстура для створення TestClient. """
    with TestClient(app) as c:
        yield c

@pytest.fixture
def user_payload():
    """ Фікстура, що повертає дані для створення користувача. """
    return {"id": 1, "name": "John Doe", "email": "john.doe@example.com"}

Використання в тесті:

def test_create_user(client, user_payload): # Pytest автоматично передасть фікстури
    response = client.post("/users/", json=user_payload)
    assert response.status_code == 201

Тестування GET-запитів

Під час тестування GET-запитів ми зазвичай перевіряємо статус-код відповіді та структуру/вміст отриманих даних.

# tests/test_main.py
from fastapi.testclient import TestClient
from app.main import app # Імпортуємо наш застосунок

# Замість фікстури можна створити клієнт глобально
# client = TestClient(app)

def test_get_users_list(client): # Використовуємо фікстуру client
    """ Тестуємо отримання списку користувачів """
    response = client.get("/users")
    assert response.status_code == 200 # Перевіряємо, що запит успішний
    # Перевіряємо, що відповідь — це JSON, і вона містить ключ "users" зі списком
    assert "users" in response.json()
    assert isinstance(response.json()["users"], list)

def test_query_params(client):
    """ Тестуємо фільтрацію через query-параметри """
    # Припускаємо, що /users?filter=Ali поверне тільки Alice
    response = client.get("/users?filter=Ali")
    assert response.status_code == 200
    assert response.json() == {"users": ["Alice"]}

Тестування POST-запитів

Під час тестування POST-запитів ми перевіряємо успішне створення ресурсу з валідними даними та коректну обробку помилок з невалідними.

# tests/test_main.py

def test_create_user_success(client, user_payload): # Використовуємо фікстури
    """ Тестуємо успішне створення користувача """
    response = client.post("/users/", json=user_payload) # Надсилаємо дані у форматі JSON
    assert response.status_code == 201 # 201 Created — стандарт для успішного POST
    assert response.json() == user_payload

def test_create_user_with_duplicate_email(client, user_payload):
    """ Тестуємо помилку при створенні користувача з існуючим email """
    # 1. Спочатку успішно створюємо користувача
    client.post("/users/", json=user_payload)

    # 2. Намагаємося створити ще одного з тими ж даними
    response = client.post("/users/", json=user_payload)
    # Припускаємо, що API поверне помилку 400 Bad Request
    assert response.status_code == 400
    assert response.json() == {"detail": "Email вже існує"}

Мокування зовнішніх API

Тести не повинні робити реальні запити до зовнішніх сервісів. Для ізоляції тестів використовується мокування (mocking) — заміна реальних об'єктів "заглушками".

Інструмент: unittest.mock (вбудований у Python), зокрема декоратор @patch.

Приклад: тестуємо ендпоінт, який звертається до зовнішнього API погоди.

# app/weather.py (код, який ми тестуємо)
import httpx
async def get_weather_data(city: str):
    async with httpx.AsyncClient() as client:
        response = await client.get(f"https://api.weather.com/forecast/{city}")
        response.raise_for_status() # Згенерує виняток, якщо статус не 2xx
        return response.json()

# tests/test_weather.py
import pytest
from unittest.mock import patch
from app.weather import get_weather_data

@pytest.mark.asyncio # Обов'язково для тестування async-функцій
@patch("app.weather.httpx.AsyncClient.get") # Вказуємо шлях до методу, який хочемо замінити
async def test_get_weather_data_mocked(mock_get):
    """ Тестуємо функцію із замоканим httpx.get """
    # Налаштовуємо mock-об'єкт: що він повинен повернути
    mock_response_payload = {"city": "London", "temp": 15}
    # Моделюємо успішну відповідь
    mock_get.return_value.status_code = 200
    mock_get.return_value.json.return_value = mock_response_payload

    # Викликаємо нашу функцію
    result = await get_weather_data("London")

    # Перевіряємо, що mock був викликаний із правильним URL
    mock_get.assert_called_once_with("https://api.weather.com/forecast/London")
    # Перевіряємо, що функція повернула дані з mock-відповіді
    assert result == mock_response_payload

Тестування обробки помилок

Важливо перевіряти, що ваше API коректно обробляє помилки та повертає правильні статус-коди й повідомлення.

Тестування помилок клієнта (4xx):

def test_read_item_not_found(client):
    """ Перевіряємо відповідь 404 для неіснуючого об'єкта """
    response = client.get("/items/999")
    assert response.status_code == 404
    assert response.json() == {"detail": "Елемент не знайдено"}

def test_create_item_invalid_payload(client):
    """ Перевіряємо відповідь 422 для невалідних даних (Pydantic) """
    # Надсилаємо дані, що не відповідають Pydantic-моделі
    invalid_payload = {"name": "TooShort", "price": "not_a_float"}
    response = client.post("/items/", json=invalid_payload)
    assert response.status_code == 422 # Помилка валідації
    # Можна перевірити і вміст відповіді про помилки
    assert "detail" in response.json()

Тестування кастомних помилок:

def test_transfer_amount_exceeds_limit(client):
    """ Перевіряємо кастомну бізнес-логіку помилки """
    # Припускаємо, що ліміт переказу $1000
    response = client.post("/transfer", json={"amount": 1500.0})
    assert response.status_code == 400 # Bad Request
    assert response.json()["detail"] == "Сума переказу перевищує ліміт у $1000.00"

Тестування аутентифікації через JWT

Перевіряємо, що захищені ендпоїнти дійсно вимагають валідний токен.

1. Тест доступу без токена:

def test_access_protected_route_no_token(client):
    """ Спроба доступу до захищеного ресурсу без токена """
    response = client.get("/protected-data")
    assert response.status_code == 401 # Unauthorized
    assert response.json()["detail"] == "Not authenticated"

2. Тест доступу з невалідним токеном:

def test_access_protected_route_invalid_token(client):
    """ Спроба доступу з недійсним токеном """
    headers = {"Authorization": "Bearer invalidtoken123"}
    response = client.get("/protected-data", headers=headers)
    assert response.status_code == 401
    assert response.json()["detail"] == "Could not validate credentials"

3. Тест доступу з валідним токеном:

# Функція-хелпер або фікстура для отримання токена
def get_valid_token(client):
    # Імітуємо логін
    response = client.post("/token", data={"username": "testuser", "password": "password"})
    return response.json()["access_token"]

def test_access_protected_route_valid_token(client):
    """ Успішний доступ із валідним токеном """
    token = get_valid_token(client)
    headers = {"Authorization": f"Bearer {token}"}
    response = client.get("/protected-data", headers=headers)
    assert response.status_code == 200
    assert "secret_data" in response.json()

Запуск тестів та аналіз покриття

Test Coverage — це метрика, що показує, який відсоток вашого коду виконався під час тестів.

Інструмент: pytest-cov

Встановлення:

pip install pytest-cov

Запуск із аналізом покриття в консолі:
Ця команда запустить тести та покаже звіт про покриття для коду в папці app.

pytest --cov=app

Результат в консолі:

----------- coverage: platform linux, python 3.10.4-final-0 -----------
Name          Stmts   Miss  Cover
---------------------------------
app/main.py      50      5    90%
---------------------------------
TOTAL            50      5    90%

Генерація HTML-звіту:

pytest --cov=app --cov-report=html

Ця команда створить папку htmlcov/. Відкрийте файл htmlcov/index.html у браузері, щоб побачити детальний інтерактивний звіт з підсвіткою непротестованих рядків коду.
