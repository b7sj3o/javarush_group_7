Рівень 9: Кешування та Redis у FastAPI

Повторювані ресурсоємні операції, будь то запити до бази даних чи зовнішніх API, неминуче сповільнюють чутливість вашого застосунку. Ми освоїмо кешування як фундаментальний метод оптимізації, а ключовим інструментом для цього стане Redis — високопродуктивна in-memory база даних типу 'ключ-значення', де-факто стандарт для кешування у вебі.

Ви дізнаєтеся, як Redis дозволяє отримувати дані за частки мілісекунд. Ми налаштуємо асинхронне підключення до Redis з aioredis, реалізуємо патерн "Cache-Aside" для ефективного кешування даних з БД, навчимося динамічно інвалідувати кеш при зміні вихідних даних та використовувати Redis для зберігання сесій користувачів.

Цей модуль дасть вам практичні навички для кардинального прискорення FastAPI-застосунків.

Що таке кешування і навіщо воно потрібне?

Кешування — це процес збереження результатів ресурсоємних операцій у швидкій пам'яті (кеші) для повторного використання. Замість того, щоб щоразу виконувати довгу операцію (наприклад, запит до бази даних чи зовнішнього API), застосунок спочатку перевіряє, чи є результат у кеші.

Навіщо це потрібно?

  • дані зі швидкої пам'яті (RAM) читаються в десятки й сотні разів швидше, ніж із диска або через мережу. API відповідає майже миттєво.
  • зменшується кількість повторюваних запитів SELECT, що звільняє ресурси БД для важливіших операцій запису.
  • швидкі та адаптивні інтерфейси подобаються користувачам.
  • знижується навантаження на CPU та мережу, зменшуються витрати на зовнішні API.

Redis — швидкий кеш і не тільки

Redis (Remote Dictionary Server) — це високопродуктивна in-memory (що працює в оперативній пам'яті) база даних типу "ключ-значення". Завдяки своїй швидкості, вона є де-факто стандартом для кешування у веб-розробці.

Переваги Redis:

  • операції читання та запису займають долі мілісекунди, оскільки всі дані знаходяться в RAM.
  • можна встановити "термін придатності" (TTL) для будь-якого ключа, після чого Redis автоматично його видалить.
  • на відміну від простих key-value сховищ, Redis підтримує рядки, списки, множини, хеші, відсортовані множини тощо.
  • дозволяє виконувати атомарні операції (наприклад, інкремент лічильника) без ризику race conditions (гонки даних).
  • може зберігати дані на диск для відновлення після перезапуску (persistence).
  • підтримує реплікацію та кластеризацію.

Встановлення та підключення Redis до FastAPI

1. Встановлення сервера Redis:

  • Docker:

    docker run --name my-redis -d -p 6379:6379 redis

2. Встановлення Python-клієнта:
Сучасна бібліотека redis-py (версії 4.2+) містить асинхронний клієнт aioredis.

pip install "redis[hiredis]" # [hiredis] — для додаткової продуктивності
pip freeze > requirements.txt

3. Асинхронне підключення в FastAPI (database.py або core/redis.py):

import redis.asyncio as redis
from contextlib import asynccontextmanager
from fastapi import FastAPI

# --- Налаштування ---
REDIS_URL = "redis://localhost:6379"

# --- Lifespan для керування підключенням ---
@asynccontextmanager
async def lifespan(app: FastAPI):
    # Підключаємося під час старту застосунку
    app.state.redis = redis.from_url(REDIS_URL, decode_responses=True)
    yield
    # Закриваємо підключення при зупинці
    await app.state.redis.close()

# --- У main.py ---
# app = FastAPI(lifespan=lifespan)
# redis_client = app.state.redis # Доступ до клієнта

Використання lifespan — це сучасний спосіб керувати ресурсами, які мають існувати протягом усього життєвого циклу застосунку.

Кешування запитів до бази даних

Це найпоширеніший сценарій використання Redis.

Патерн "Cache-Aside":

  1. Згенерувати унікальний ключ для запиту.
  2. Спробувати отримати дані за цим ключем із Redis.
  3. Якщо дані в кеші є (cache hit): повернути їх.
  4. Якщо даних немає (cache miss):
    1. Зробити запит до основної бази даних.
    2. Серіалізувати отримані дані (наприклад, у JSON).
    3. Зберегти серіалізовані дані в Redis зі встановленим TTL.
    4. Повернути дані клієнту.
graph TD A[Клієнтський запит] --> B{Дані є в кеші?}; B -- Так (Cache Hit) --> C[Віддати дані з Redis]; C --> F[Відповідь клієнту]; B -- Ні (Cache Miss) --> D[Запитати дані з основної БД]; D --> E[Зберегти результат в Redis з TTL]; E --> F; style C fill:#cfc,stroke:#333,stroke-width:2px; style D fill:#f99,stroke:#333,stroke-width:2px;

Приклад (ендпоінт для отримання списку товарів):

import json
from fastapi import Depends

# ... (припускаємо, що redis_client доступний)

@app.get("/products")
async def get_products():
    cache_key = "all_products"
    # 1. Перевіряємо кеш
    cached_products = await redis_client.get(cache_key)
    if cached_products:
        return json.loads(cached_products) # Повертаємо з кеша

    # 2. Якщо в кеші немає — йдемо до БД
    products_from_db = await get_all_products_from_db() # Функція для запиту до БД
    products_json = json.dumps(products_from_db) # Серіалізуємо

    # 3. Зберігаємо до кеша з TTL на 60 секунд
    await redis_client.setex(cache_key, 60, products_json)

    return products_from_db

Динамічні ключі та інвалідація кеша

Для кешування даних, що залежать від параметрів (наприклад, профіль конкретного користувача), ключ має бути унікальним.

# Добрий ключ для профілю користувача
cache_key = f"user_profile:{user_id}"
# Поганий ключ: "user_profile" — закешує дані лише одного користувача

Коли вихідні дані в базі даних змінюються (UPDATE або DELETE), відповідний кеш стає неактуальним. Його необхідно видалити (інвалідувати).

Стратегії інвалідації:

  1. TTL (Time To Live): найпростіша. Дані просто "протухнуть" після встановленого часу. Підходить, якщо некритично показувати трохи застарілі дані.
  2. Явна інвалідація: під час зміни даних у БД, ви явно видаляєте відповідний ключ із Redis.

Приклад явної інвалідації:

@app.put("/users/{user_id}")
async def update_user(user_id: int, user_data: UserUpdate):
    # ... (логіка оновлення користувача в БД) ...
    updated_user = await update_user_in_db(user_id, user_data)

    # Після успішного оновлення в БД, видаляємо старі дані з кеша
    cache_key = f"user_profile:{user_id}"
    await redis_client.delete(cache_key)

    return updated_user

Кешування користувацьких сесій

Redis чудово підходить для зберігання даних сесій, особливо в розподілених системах, де у вас є кілька екземплярів FastAPI.

Процес:

  1. Після успішного логіна користувача генерується унікальний ID сесії (наприклад, UUID).
  2. Дані користувача (або його ID) зберігаються в Redis за цим ID сесії як ключем. Встановлюється TTL (наприклад, година).
  3. ID сесії надсилається клієнту (в cookie або в тілі відповіді).
  4. Під час кожного запиту до захищених ендпоінтів клієнт передає свій ID сесії.
  5. Сервер перевіряє наявність цього ID у Redis. Якщо ключ є — користувач автентифікований. Якщо ні — сесія завершилася або є невалідною.

Спрощений приклад:

from uuid import uuid4
from fastapi import Cookie, HTTPException, Response

@app.post("/login")
async def login(response: Response, username: str):
    session_id = str(uuid4())
    # Зберігаємо username в Redis на 1 годину (3600 с)
    await redis.setex(f"session:{session_id}", 3600, username)
    # Встановлюємо session_id в httpOnly cookie
    response.set_cookie(key="session_id", value=session_id, httponly=True)
    return {"message": "Успішний вхід"}

@app.get("/profile/me")
async def get_my_profile(session_id: str = Cookie(None)):
    if not session_id:
        raise HTTPException(status_code=401, detail="Not authenticated")
    username = await redis.get(f"session:{session_id}")
    if not username:
        raise HTTPException(status_code=401, detail="Session expired or invalid")
    return {"username": username}

Асинхронна взаємодія з aioredis

Усі операції з Redis в асинхронному застосунку мають бути асинхронними. redis-py надає для цього asyncio API.

Основні асинхронні методи:

  • await redis.get(key): отримати значення за ключем.
  • await redis.set(key, value): встановити значення.
  • await redis.setex(key, ttl_seconds, value): встановити значення з TTL.
  • await redis.delete(key): видалити ключ.
  • await redis.incr(key): атомарно збільшити значення ключа на 1.
  • await redis.lpush(list_key, value): додати елемент на початок списку.
  • await redis.lrange(list_key, start, end): отримати зріз списку.

Приклад:

@app.post("/page-views/{page_slug}")
async def increment_page_view(page_slug: str):
    # Атомарно збільшуємо лічильник переглядів для сторінки
    view_count = await redis.incr(f"page_views:{page_slug}")
    return {"page": page_slug, "views": view_count}

@app.get("/page-views/{page_slug}")
async def get_page_view(page_slug: str):
    view_count = await redis.get(f"page_views:{page_slug}")
    return {"page": page_slug, "views": int(view_count or 0)}

Політики витіснення та моніторинг

Оскільки Redis зберігає дані в оперативній пам'яті, її обсяг обмежений. Що станеться, коли пам'ять закінчиться?

Політики витіснення (Eviction Policies):

  • ви налаштовуєте в конфігурації Redis, як він має поводитися в разі нестачі пам'яті.
  • volatile-lru (часто використовується для кеша): видаляти ключі зі встановленим TTL, які найдовше не використовувались.
  • allkeys-lru: видаляти ключі, які найдовше не використовувались, з-поміж усіх ключів.
  • volatile-ttl: видаляти ключі з найменшим залишковим часом життя.
  • noeviction (за замовчуванням): нічого не видаляти, повертати помилку при спробі запису.

Моніторинг:

  • важливо стежити за станом Redis.
  • INFO MEMORY: команда для перегляду використання пам'яті.
  • MONITOR: команда для перегляду всіх виконуваних команд у реальному часі (для відладки).
  • Інструменти: для продакшену використовуються системи моніторингу, такі як Prometheus з Redis Exporter та Grafana для візуалізації.
