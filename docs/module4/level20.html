Рівень 20: Комплексна система обробки помилок

Неповна обробка помилок — одна з головних причин збоїв, поганого користувацького досвіду та нескінченних проблем з налагодженням у будь-якому API. Ми поглибимо розуміння цієї критично важливої теми, створюючи повну та стійку систему обробки помилок у FastAPI.

Ви навчитеся чітко розрізняти помилки клієнта (4xx) та сервера (5xx), ефективно використовуючи HTTPException. Ми освоїмо створення кастомних обробників винятків для специфічної бізнес-логіки та глобального обробника для Exception як останньої лінії захисту. Також буде розглянуто використання Middleware для централізованого перехоплення та логування помилок.

Особливу увагу приділимо правильному логуванню помилок з докладною інформацією (exc_info=True), інтеграції із зовнішніми системами моніторингу та стратегіям обробки помилок при взаємодії із зовнішніми API, що дозволить вашому застосунку бути по-справжньому відмовостійким та інформативним.

Чому обробка помилок — це важливо?

Коректна обробка помилок — це не просто try...except. Це фундаментальна частина створення надійного та безпечного API.

  1. Розрізняйте помилки клієнта та сервера:

    • 4xx (Client Errors): помилка в запиті клієнта (невалідні дані, немає прав, ресурс не знайдено). Клієнт може виправити помилку та повторити запит.
    • 5xx (Server Errors): помилка на вашому боці (баг у коді, недоступність БД). Клієнт не може це виправити.

  2. Інформуйте клієнта, але не розкривайте деталі:

    • клієнту: "Користувач з таким email вже існує" (400) або "Сталася внутрішня помилка, спробуйте пізніше" (500).
    • розробнику (в логах): повний traceback, ID запиту, дані користувача.
  3. Логуйте всі непередбачені помилки: будь-яка 5xx відповідь має супроводжуватися детальним записом у логах.
  4. Будьте послідовними: використовуйте єдиний формат для відповідей про помилки в усьому API.

Базова обробка: HTTPException

Найпростіший і найпоширеніший спосіб повернути HTTP-помилку з ендпоінта — це згенерувати виняток HTTPException.

Імпорт: from fastapi import HTTPException

Використання: raise HTTPException(status_code=..., detail=...)

  • status_code: код стану HTTP (наприклад, 404, 400, 403).
  • detail: повідомлення про помилку, яке надіслано клієнту в JSON-відповіді.
  • headers: опціональний словник із додатковими заголовками.

FastAPI автоматично перехопить цей виняток і сформує коректну JSON-відповідь.

from fastapi import FastAPI, HTTPException

app = FastAPI()
items_db = {1: "Яблуко", 2: "Банан"}

@app.get("/items/{item_id}")
async def read_item(item_id: int):
    if item_id not in items_db:
        # Якщо товар не знайдено, повертаємо 404
        raise HTTPException(status_code=404, detail="Товар не знайдено")

    # Тут може бути перевірка прав
    # if not user_has_permission_to_view(item_id):
    #     raise HTTPException(status_code=403, detail="Недостатньо прав")

    return {"item": items_db[item_id]}

Кастомні обробники винятків

Що робити, якщо ви хочете мати єдиний формат для всіх помилок певного типу або обробляти винятки, які ви не генерували напряму (наприклад, з бібліотек)? Для цього використовуються обробники винятків.

Процес:

  1. Написати асинхронну функцію-обробник.
  2. Зареєструвати її за допомогою декоратора @app.exception_handler(ExceptionType).

Приклад: кастомний виняток для бізнес-логіки

from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

# 1. Створюємо власний виняток
class InsufficientFundsError(Exception):
    def __init__(self, balance: float, amount: float):
        self.balance = balance
        self.amount = amount

app = FastAPI()

# 2. Реєструємо для нього обробник
@app.exception_handler(InsufficientFundsError)
async def insufficient_funds_exception_handler(request: Request, exc: InsufficientFundsError):
    return JSONResponse(
        status_code=400,
        content={
            "error_code": "INSUFFICIENT_FUNDS",
            "message": f"Недостатньо коштів. Баланс: {exc.balance}, Зроблено запит на: {exc.amount}"
        },
    )

# 3. Використовуємо виняток в ендпоінті
@app.post("/withdraw")
async def withdraw(amount: float):
    current_balance = 50.0 # Заглушка
    if amount > current_balance:
        raise InsufficientFundsError(balance=current_balance, amount=amount)
    return {"message": "Кошти успішно знято"}

Глобальний обробник помилок

Щоб перехоплювати всі необроблені винятки та уникати падіння застосунку з 500 Internal Server Error, можна створити глобальний обробник для базового класу Exception.

import logging
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()
logger = logging.getLogger(__name__)

@app.exception_handler(Exception)
async def global_exception_handler(request: Request, exc: Exception):
    # Логуємо повний traceback для налагодження
    logger.error(f"Необроблений виняток: {exc}", exc_info=True)
    # Повертаємо користувачу загальне повідомлення
    return JSONResponse(
        status_code=500,
        content={"message": "Сталася непередбачена помилка на сервері."},
    )

@app.get("/bug")
async def cause_an_error():
    # Цей код викличе ZeroDivisionError
    result = 1 / 0
    return {"result": result}

Важливо! Цей обробник має бути останнім і найзагальнішим, щоб не перехоплювати більш специфічні винятки, для яких у вас є власні обробники.

Middleware для обробки помилок

Middleware — це ще один спосіб централізованої обробки помилок. Middleware "огортає" кожен запит.

Коли використовувати Middleware:

  • коли потрібно застосувати однакову логіку (наприклад, логування) до всіх запитів та помилок.
  • коли потрібно виконати дії до або після основної логіки ендпоінта.
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse
from starlette.middleware.base import BaseHTTPMiddleware
import logging

logger = logging.getLogger(__name__)

class ErrorHandlingMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        try:
            # Передаємо запит далі за ланцюжком
            response = await call_next(request)
            return response
        except Exception as e:
            # Якщо десь нижче (в іншому middleware або ендпоінті) виник виняток
            logger.error(f"Помилка під час обробки запиту {request.url}: {e}", exc_info=True)
            return JSONResponse(
                status_code=500,
                content={"detail": "Сталася внутрішня помилка сервера."},
            )

app = FastAPI()
app.add_middleware(ErrorHandlingMiddleware)

Ієрархія: запит спочатку проходить через Middleware, потім потрапляє до ендпоінта. Якщо ендпоінт генерує виняток, він "спливає" вгору і може бути перехоплений Middleware або обробником @app.exception_handler. Обробники @app.exception_handler мають вищий пріоритет, ніж Middleware.

Логування помилок

Просто повернути користувачу красивий JSON недостатньо. Ви повинні знати про помилки, щоб їх виправляти.

  • використовуйте стандартний модуль logging: він гнучкий та розширюваний.
  • налаштуйте формат: логи повинні містити дату, час, рівень, назву логера та саме повідомлення.
  • логуйте з exc_info=True: для винятків це додасть до логу повний traceback, що є критично важливим для налагодження.
  • використовуйте різні рівні:
    • INFO: для звичайних подій (запуск сервера, успішна обробка важливої операції).
    • WARNING: для некритичних проблем, на які варто звернути увагу.
    • ERROR: для помилок, що вимагають втручання (необроблені винятки, збої).
    • CRITICAL: для помилок, що призводять до падіння всього застосунку.
  • у продакшені: налаштуйте надсилання логів до файлів або централізованих систем (Sentry, ELK Stack, Datadog).
# Приклад налаштування в коді (у продакшені краще використовувати dictConfig)
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s - %(levelname)s - %(name)s - %(message)s",
    handlers=[
        logging.FileHandler("app.log"), # Пишемо у файл
        logging.StreamHandler(),      # І виводимо в консолі
    ],
)

Обробка помилок у роботі із зовнішніми API

Як ви вже знаєте з попередніх рівнів, у роботі із зовнішніми сервісами потрібно бути готовим до збоїв.

Ієрархія обробки:

graph TD A[Ендпоінт FastAPI] --> B(Виклик сервісної функції); subgraph Сервісний шар services.py B --> C{try...except httpx.HTTPStatusError}; C -- Помилка 4xx/5xx --> D[raise CustomAPIError]; B --> E{try...except httpx.RequestError}; E -- Мережева помилка --> F[raise CustomConnectionError]; end D --> G{"Обробник
@app.exception_handler(CustomAPIError)"}; F --> H{"Обробник
@app.exception_handler(CustomConnectionError)"}; G --> I[Відповідь клієнту 400 або 502]; H --> J[Відповідь клієнту 503]

Пояснення:

  1. Ваш ендпоінт викликає функцію із сервісного шару.
  2. Сервісна функція обгортає запит httpx у try...except, перехоплює специфічні помилки httpx і "перекидає" їх як ваші власні, зрозумілі кастомні винятки (CustomAPIError, CustomConnectionError).
  3. FastAPI перехоплює ці кастомні винятки за допомогою @app.exception_handler і формує стандартизовану відповідь для клієнта.

Цей підхід розділяє відповідальність: сервісний шар знає про помилки httpx, а шар API — лише про ваші внутрішні винятки.

Повна система: ієрархія обробників

FastAPI обробляє винятки в такому порядку пріоритету (від найвищого до найнижчого):

  1. Вбудовані обробники Starlette/FastAPI: (HTTPException, помилки валідації Pydantic). Вони спрацьовують першими.
  2. Кастомні обробники @app.exception_handler(ExceptionType): перехоплюють конкретні, вказані вами винятки.
  3. Middleware: перехоплюють усе, що "пролетіло" повз ендпоінт і не було перехоплено більш специфічним обробником.
  4. Глобальний обробник @app.exception_handler(Exception): перехоплює абсолютно все інше, що не оброблено раніше.

Рекомендація:

  • використовуйте HTTPException для ймовірних помилок в ендпоінтах.
  • використовуйте кастомні винятки та @app.exception_handler для помилок бізнес-логіки та помилок від зовнішніх сервісів.
  • використовуйте глобальний обробник @app.exception_handler(Exception) як останню лінію захисту для логування та повернення загального повідомлення про серверну помилку.
  • використовуйте Middleware для наскрізної логіки, як-от додавання ID запиту до логів.
