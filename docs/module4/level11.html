Рівень 11: Транзакції, зв'язки та оптимізація в SQLAlchemy

Взаємодія з базою даних через ORM відкриває безліч можливостей, але також ставить питання забезпечення цілісності даних, ефективної роботи зі зв'язками та оптимізації продуктивності. Ми поглибимо наші знання про SQLAlchemy, сфокусувавшись на транзакціях — фундаментальній концепції, що гарантує атомарність операцій та дотримання властивостей ACID.

Ви навчитеся керувати транзакціями в асинхронному SQLAlchemy за допомогою контекстних менеджерів. Ми повторимо різні типи зв'язків між таблицями та освоїмо методи selectinload і joinedload для вирішення наболілої проблеми N+1 запитів.

Також розглянемо агрегації, підзапити, методи потокової обробки великих обсягів даних та інструменти для профілювання SQL-запитів, щоб ваш API працював максимально ефективно.

Що таке транзакція і навіщо вона потрібна?

Транзакція — це послідовність операцій з базою даних, яка виконується як єдине ціле. Це фундаментальна концепція для забезпечення цілісності даних.

Принцип "все або нічого":

  • Якщо всі операції всередині транзакції завершуються успішно, їхні результати фіксуються (commit) і стають постійними.
  • Якщо хоча б одна операція завершується збоєм, усі попередні зміни в межах цієї транзакції відкочуються (rollback), ніби нічого й не відбувалося.

Приклад із життя: банківський переказ. Списання грошей з одного рахунку та зарахування на інший мають відбутися разом. Якщо списання вдалося, а зарахування — ні, всю операцію має бути скасовано.

Властивості ACID

Надійні транзакційні системи мають властивості ACID:

  • Atomicity (Атомарність): транзакція є атомарною — вона або виконується повністю, або не виконується взагалі. Немає проміжних станів.
  • Consistency (Консистентність): транзакція переводить базу даних з одного узгодженого стану в інший. Усі правила та обмеження (constraints) бази даних дотримуються.
  • Isolation (Ізольованість): паралельні транзакції не повинні заважати одна одній. Результати однієї транзакції невидимі для інших, поки вона не буде зафіксована.
  • Durability (Довговічність): після успішного завершення (commit) транзакції її результати зберігаються назавжди, навіть у разі збою системи (наприклад, відключення живлення).

Транзакції в асинхронному SQLAlchemy

В асинхронному SQLAlchemy керування транзакціями зазвичай відбувається за допомогою контекстного менеджера async with session.begin():.

Явне керування (менш бажаний спосіб):

await session.begin()
try:
    # ... операції з session.add(), await session.execute() ...
    await session.commit()
except Exception:
    await session.rollback()
    raise

Контекстний менеджер (рекомендований спосіб):
async with session.begin(): автоматично починає транзакцію. Якщо блок коду завершується без винятків, транзакція автоматично комітиться. Якщо виникає виняток, транзакція автоматично відкочується.

# session отримана із залежності Depends(get_async_session)
try:
    async with session.begin():
        # ... операції з session.add(), await session.execute() ...
        # commit буде викликаний автоматично під час виходу з блоку
    return {"status": "success"}
except SQLAlchemyError:
    # rollback буде викликаний автоматично у разі виникнення винятку
    raise HTTPException(status_code=500, detail="Database error")

Транзакції для пов'язаних операцій

Використовуйте одну транзакцію для виконання кількох залежних дій.

Приклад: створення замовлення та зменшення залишку товару

from sqlalchemy.exc import SQLAlchemyError

async def create_order(
    item_id: int, quantity: int, session: AsyncSession = Depends(get_async_session)
):
    try:
        async with session.begin(): # Починаємо транзакцію
            # Отримуємо товар із блокуванням для оновлення (FOR UPDATE)
            item_stmt = select(Item).where(Item.id == item_id).with_for_update()
            item = (await session.execute(item_stmt)).scalar_one()

            if item.stock < quantity:
                raise ValueError("Недостатньо товару на складі")

            # Зменшуємо залишок
            item.stock -= quantity

            # Створюємо замовлення
            new_order = Order(item_id=item_id, quantity=quantity)
            session.add(new_order)

            # session.commit() викличеться автоматично
    except ValueError as e:
        # session.rollback() викличеться автоматично
        raise HTTPException(status_code=400, detail=str(e))
    except SQLAlchemyError:
        raise HTTPException(status_code=500, detail="Помилка бази даних")

Зв'язки між таблицями

Нагадаємо, як визначаються зв'язки в SQLAlchemy з використанням relationship.

One-to-One (uselist=False):

# В моделі User
profile: Mapped["Profile"] = relationship(back_populates="user", uselist=False)
# В моделі Profile
user: Mapped["User"] = relationship(back_populates="profile")
user_id: Mapped[int] = mapped_column(ForeignKey('users.id'))

Foreign Key (One-to-Many):

# В моделі Author (сторона "один")
books: Mapped[List["Book"]] = relationship(back_populates="author")
# В моделі Book (сторона "багато")
author_id: Mapped[int] = mapped_column(ForeignKey('authors.id'))
author: Mapped["Author"] = relationship(back_populates="books")

Many-to-Many (secondary):

# В моделі Post
tags: Mapped[List["Tag"]] = relationship(secondary=post_tag_association, ...)
# В моделі Tag
posts: Mapped[List["Post"]] = relationship(secondary=post_tag_association, ...)

Оптимізація запитів: selectinload та joinedload

Проблема N+1 запитів так само актуальна для SQLAlchemy, як і для Django ORM.

  • Lazy Loading (ліниве завантаження): за замовчуванням, пов'язані об'єкти завантажуються лише в момент першого звернення до них. Це зручно, але в циклах призводить до N+1 запитів.
  • Eager Loading ("жадібне" завантаження): дозволяє завантажити пов'язані дані заздалегідь, в одному або кількох запитах.

Інструменти Eager Loading:

  • joinedload():

    • використовує LEFT OUTER JOIN для завантаження пов'язаних об'єктів в одному SQL-запиті.
    • ідеально для зв'язків -to-one (ForeignKey, OneToOneField).
    • може бути неефективним для зв'язків -to-many через дублювання даних основного об'єкта.

  • selectinload():

    • виконує другий SQL-запит (SELECT ... WHERE id IN (...)) для завантаження пов'язаних об'єктів.
    • ідеально для зв'язків -to-many (ManyToManyField, зворотний ForeignKey).

Приклад:

from sqlalchemy.orm import selectinload, joinedload

# Завантажити пости, їхніх авторів (JOIN) та теги (другий запит)
statement = (
    select(Post)
    .options(
        joinedload(Post.author),     # Для ForeignKey
        selectinload(Post.tags)      # Для ManyToMany
    )
)
result = await session.execute(statement)
posts = result.scalars().unique().all()

# Тепер доступ до post.author та post.tags не викличе додаткових запитів у циклі
for post in posts:
    print(post.author.name)
    for tag in post.tags:
        print(tag.name)

Агрегації та підзапити

  • Агрегація: обчислення підсумкових значень (COUNT, AVG, SUM). Використовується sqlalchemy.func.
  • Підзапит: вкладений запит, результат якого використовується в основному запиті.

Приклад агрегації:

from sqlalchemy import func, select

# Порахувати кількість користувачів
count_statement = select(func.count(User.id))
user_count = (await session.execute(count_statement)).scalar_one() # .scalar_one() для одного значення

# Знайти середній вік
avg_age_statement = select(func.avg(User.age))
avg_age = (await session.execute(avg_age_statement)).scalar_one()

Приклад підзапиту:

# Знайти всіх користувачів, чий вік вищий за середній

# 1. Створюємо підзапит для обчислення середнього віку
subquery = select(func.avg(User.age)).scalar_subquery()

# 2. Використовуємо його в основному запиті
main_query = select(User).where(User.age > subquery)

result = await session.execute(main_query)
users_above_average_age = result.scalars().all()

Робота з великими обсягами даних

Обробка тисяч або мільйонів рядків вимагає спеціальних підходів, щоб не вичерпати оперативну пам'ять.

Потокова обробка (Streaming / Chunking):
Замість завантаження всіх результатів одразу (.all()) обробляйте їх частинами (.stream() або .partitions()).

from sqlalchemy import select

statement = select(HugeTable)
# .stream() повертає асинхронний ітератор
async for row in await session.stream(statement):
    # Обробляємо один рядок (row) за раз
    # Споживання пам'яті мінімальне
    process_row(row)

# Обробка "пачками" (chunks) по 1000 рядків
result = await session.execute(statement)
for partition in result.partitions(1000):
    process_batch(partition) # partition — це список з 1000 рядків

Асинхронність та паралелізм (наприклад, з asyncio.gather) також можуть значно прискорити обробку.

Тестування та профілювання SQL-запитів

Щоб переконатися, що ваші запити є ефективними, їх потрібно аналізувати.

1. Логування запитів у SQLAlchemy:
Увімкніть echo=True при створенні `engine`, щоб виводити всі згенеровані SQL-запити в консолі.

engine = create_async_engine(DATABASE_URL, echo=True)

2. Аналіз плану виконання (EXPLAIN ANALYZE):
Це команда самої СУБД (наприклад, PostgreSQL), яка показує, як саме база даних виконує ваш запит: які індекси використовує, які типи сканування таблиць тощо.

# У psql або іншому клієнті БД
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@example.com';

Якщо ви бачите Seq Scan (послідовне сканування) на великій таблиці, це явна ознака відсутності потрібного індексу.

3. Інструменти для FastAPI:

  • django-debug-toolbar тут не підходить, оскільки це інструмент для Django.
  • Сторонні Middleware: можна використовувати middleware, що вимірюють час виконання запитів та логують їх (наприклад, fastapi-sqlalchemy-profiler).

Практичні поради з оптимізації

Індекси: додавайте індекси (index=True) на поля, що використовуються в WHERE, JOIN та ORDER BY. Не створюйте зайвих індексів, оскільки вони уповільнюють операції запису (INSERT, UPDATE, DELETE).

Eager loading: завжди використовуйте selectinload та joinedload в ендпоінтах, які повертають списки пов'язаних даних, щоб уникнути проблеми N+1.

Короткі транзакції: тримайте блоки транзакцій (async with session.begin():) якомога коротшими та швидшими. Не виконуйте в них повільних операцій, як-от зовнішні API-виклики.

Профілюйте: не оптимізуйте наосліп. Використовуйте логування та EXPLAIN ANALYZE для пошуку реальних "вузьких місць" у продуктивності.
