Рівень 12: Асинхронні черги повідомлень та RabbitMQ

Синхронні REST API можуть стати вузьким місцем, коли операції потребують багато часу, роблячи ваш застосунок нечутливим та ускладнюючи масштабування. Ми зануримося у світ асинхронних черг повідомлень, які дозволяють сервісам взаємодіяти незалежно, і сфокусуємося на RabbitMQ — одному з найнадійніших брокерів повідомлень.

Ви зрозумієте, навіщо черги потрібні для виконання фонових задач, розберете ключові компоненти RabbitMQ (обмінники, черги, продюсери, консьюмери) та різні типи обмінників для гнучкої маршрутизації повідомлень. Ми навчимося встановлювати та налаштовувати RabbitMQ, а потім інтегруємо його у FastAPI за допомогою асинхронної бібліотеки aio-pika, створюючи надійних продюсерів та консьюмерів, здатних обробляти дані без втрат навіть при перезапусках.

Що таке черги повідомлень і навіщо вони потрібні?

Черга повідомлень — це механізм асинхронної взаємодії між компонентами системи (сервісами). Один компонент, продюсер (Producer), надсилає повідомлення (завдання) в чергу, не чекаючи на її виконання. Інший компонент, консюмер (Consumer), забирає це повідомлення з черги та обробляє його у власному темпі.

Навіщо це потрібно?

  • асинхронність: ваш основний сервіс (наприклад, FastAPI) не "зависає" на довгих завданнях. Він швидко відповідає користувачу "завдання прийнято", а реальна робота відбувається у фоновому режимі.
  • масштабованість: якщо завдання накопичуються, ви можете просто запустити більше консюмерів для "розгрібання" черги.
  • відмовостійкість: якщо консюмер "падає", повідомлення залишається в черзі і буде оброблене пізніше або іншим консюмером. Якщо "падає" продюсер, консюмери продовжують працювати з тим, що є в черзі.
  • розв'язка сервісів (decoupling): продюсер і консюмер нічого не знають один про одного, крім формату повідомлення. Їх можна розробляти, оновлювати та розгортати незалежно.

Принцип роботи черги

Продюсер і консюмер не зв'язані напряму, а взаємодіють через чергу.

Черги vs REST API

Сценарій REST API (Синхронно) Черга повідомлень (Асинхронно)
Взаємодія клієнт надсилає запит і чекає на відповідь продюсер надсилає повідомлення і не чекає на його обробку
Час відповіді дорівнює часу виконання завдання майже миттєва відповідь ("завдання прийнято")
Приклад: Генерація звіту користувач натискає "згенерувати" і чекає хвилину, поки сторінка "завантажується" користувач натискає "згенерувати", бачить "звіт буде готовий за хвилину", і може продовжувати роботу
Ідеально для швидких операцій, отримання даних (CRUD) довгих, фонових, ресурсоємних завдань

Використовуйте черги для завдань, які не вимагають негайної відповіді: надсилання email-розсилок, обробка завантажених файлів, застосування AI-моделей, складні обчислення.

Вступ до RabbitMQ

RabbitMQ — це один із найпопулярніших та найнадійніших брокерів повідомлень. Він діє як "поштове відділення" для повідомлень у вашій системі. RabbitMQ реалізує протокол AMQP (Advanced Message Queuing Protocol).

Ключові компоненти RabbitMQ:

  • Producer: застосунок, що надсилає повідомлення.
  • Consumer: застосунок, що отримує та обробляє повідомлення.
  • Queue: буфер, який зберігає повідомлення.
  • Exchange: точка входу для повідомлень. Продюсер надсилає повідомлення саме в exchange, а не напряму в чергу. Exchange вирішує, в які черги спрямувати повідомлення, на основі своїх правил та типу.

Компоненти RabbitMQ

graph TD P[Producer] -- Повідомлення --> E(Exchange); E -- Правило маршрутизації --> Q1[Queue A]; E -- Правило маршрутизації --> Q2[Queue B]; Q1 --> C1[Consumer 1]; Q2 --> C2[Consumer 2]; style E fill:#f9f,stroke:#333,stroke-width:2px;

Продюсер надсилає повідомлення в exchange, який, наче поштовий сортувальник, розподіляє його потрібними чергами (Queues).

Типи exchange в RabbitMQ

Тип exchange визначає його логіку маршрутизації повідомлень.

Direct:

  • принцип: повідомлення надсилається до черги, якщо routing_key (ключ маршрутизації) повідомлення точно збігається з binding_key (ключ прив'язки) черги.
  • використання: для точкової доставки повідомлень конкретному обробнику (unicast).

Fanout:

  • принцип: повідомлення надсилається до всіх прив'язаних до exchange черг, routing_key ігнорується.
  • використання: для масової розсилки повідомлень (broadcast), наприклад, для сповіщення всіх сервісів про подію.

Topic:

  • принцип: повідомлення надсилається до черг, чий binding_key відповідає шаблону routing_key повідомлення. Використовуються символи * (одне слово) та # (нуль або більше слів).
  • використання: для гнучкої маршрутизації за темами. Приклад routing_key: logs.user.error. Приклад binding_key: logs.# (отримати всі логи) або logs.*.error (отримати всі помилки).

Headers:

  • принцип: маршрутизація базується на збігу заголовків (headers) повідомлення, а не routing_key.
  • використання: для складних правил маршрутизації, що не базуються на рядкових ключах.

Встановлення та базове налаштування RabbitMQ

1. Встановлення:

  • Docker:

    # Запускаємо RabbitMQ з вебінтерфейсом керування
docker run -d --hostname my-rabbit --name some-rabbit -p 5672:5672 -p 15672:15672 rabbitmq:3-management
  • Локальна установка: вимагає встановлення Erlang, а потім RabbitMQ Server.

2. Вебінтерфейс (Management Plugin):

  • якщо ви використовували образ rabbitmq:3-management, інтерфейс вже увімкнений.
  • доступ: http://localhost:15672
  • логін/пароль за замовчуванням: guest / guest
  • можливості: перегляд черг, exchange-ів, з'єднань; надсилання/отримання повідомлень вручну; керування користувачами та правами доступу.

3. Користувачі та права:

  • Користувач guest за замовчуванням може підключатися лише з localhost.
  • Для продакшену необхідно створити окремого користувача з паролем та надати йому права на певні віртуальні хости (vhosts).

Асинхронна інтеграція з FastAPI

Для асинхронної роботи з RabbitMQ з FastAPI використовується бібліотека aio-pika.

Встановлення:

pip install aio-pika
pip freeze > requirements.txt

Приклад асинхронного продюсера (в ендпоінті FastAPI):

import aio_pika
from fastapi import FastAPI

app = FastAPI()

@app.post("/send-task/")
async def send_task_to_queue(message: str):
    # Підключаємось до RabbitMQ
    connection = await aio_pika.connect_robust("amqp://guest:guest@localhost/")
    async with connection:
        # Створюємо канал
        channel = await connection.channel()
        # Надсилаємо повідомлення напряму в чергу (використовується default exchange)
        await channel.default_exchange.publish(
            aio_pika.Message(body=message.encode()),
            routing_key="hello_queue", # Назва черги
        )
    return {"status": "Повідомлення надіслано до черги"}

Приклад асинхронного консюмера (окремий скрипт-воркер):

# worker.py
import asyncio
import aio_pika

async def main():
    connection = await aio_pika.connect_robust("amqp://guest:guest@localhost/")
    async with connection:
        channel = await connection.channel()
        # Оголошуємо чергу (щоб переконатися, що вона існує)
        queue = await channel.declare_queue("hello_queue", durable=True)
        # Починаємо слухати чергу
        async with queue.iterator() as queue_iter:
            async for message in queue_iter:
                async with message.process(): # Підтверджує отримання повідомлення після обробки
                    print(f"Отримано та оброблено: {message.body.decode()}")

if __name__ == "__main__":
    asyncio.run(main())

Надійність: durable черги та persistent повідомлення

За замовчуванням, якщо сервер RabbitMQ перезавантажиться, усі черги та повідомлення в них зникнуть. Щоб цього уникнути, потрібно використовувати:

  • Стійкі (durable) черги:

    • черга буде відновлена після перезавантаження сервера.
    • оголошується з прапором durable=True.
    queue = await channel.declare_queue("my_durable_queue", durable=True)

  • Стійкі (persistent) повідомлення:

    • повідомлення збережеться на диск і переживе перезавантаження.
    • створюється з delivery_mode=aio_pika.DeliveryMode.PERSISTENT.
    await exchange.publish(
    aio_pika.Message(
        body=b"Persistent message",
        delivery_mode=aio_pika.DeliveryMode.PERSISTENT
    ),
    routing_key="my_durable_queue"
)
Важливо!

Для гарантії доставки потрібно використовувати підтвердження (acknowledgements). У aio-pika контекстний менеджер async with message.process(): автоматично надсилає підтвердження (ack) після успішного виконання блоку коду. Якщо в блоці станеться помилка, підтвердження не буде надіслано, і RabbitMQ передасть повідомлення іншому консюмеру.
