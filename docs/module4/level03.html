Рівень 3: Валідація даних з Pydantic

Ручна валідація вхідних та вихідних даних — виснажливе, схильне до помилок завдання, яке засмічує код. Pydantic — це фундаментальна бібліотека, яка перетворює цей процес на задоволення, використовуючи стандартні анотації типів Python.

Ми дізнаємося, як Pydantic автоматично парсить, валідує та серіалізує дані, позбавляючи вас від ручних перевірок. Ви навчитеся створювати базові та вкладені моделі для опису складних структур, використовувати функцію Field для додавання суворих обмежень та писати кастомні валідатори.

Окремо розглянемо response_model, який не тільки гарантує коректну структуру відповіді, але й запобігає витоку чутливих даних, а також автоматично генерує схеми для OpenAPI.

Що таке Pydantic і навіщо він потрібен?

Pydantic — це бібліотека Python для парсингу, валідації, серіалізації та документування даних. Вона використовує стандартні анотації типів Python (str, int, bool тощо) для визначення структури даних.

У контексті FastAPI Pydantic є фундаментальним інструментом, який:

  • автоматично перевіряє, що дані, які надходять до вашого API (і виходять із нього), відповідають очікуваній структурі й типам.
  • позбавляє необхідності писати безліч ручних перевірок (if type(data['id']) is not int: ...).
  • надає детальні повідомлення про помилки, якщо дані невалідні.
  • FastAPI використовує Pydantic-моделі для автоматичної генерації схем даних у Swagger/OpenAPI.

Створення базової Pydantic-моделі

Модель даних у Pydantic визначається як клас, що успадковує pydantic.BaseModel. Поля моделі оголошуються як атрибути класу з використанням анотацій типів.

from pydantic import BaseModel
from typing import Optional # Для опціональних полів

class Item(BaseModel):
    # Обов'язкові поля
    id: int
    name: str
    price: float

    # Опціональне поле зі значенням None за замовчуванням
    description: Optional[str] = None

    # Поле з іншим значенням за замовчуванням
    is_offer: bool = False

Цей клас Item тепер є "схемою" або "контрактом" для ваших даних. FastAPI використовуватиме його для валідації.

Автоматична валідація та перетворення типів

Pydantic не лише перевіряє типи, а й намагається перетворити вхідні дані до очікуваного типу, якщо це можливо.

Приклад:

from pydantic import BaseModel

class User(BaseModel):
    id: int
    name: str
    is_active: bool

# Вхідні дані (наприклад, з JSON, де все може бути рядками)
user_data = {
    "id": "123", # Рядок, але може бути перетворений на int
    "name": "Alex",
    "is_active": "true" # Рядок, але може бути перетворений на bool
}

# Pydantic парсить і перетворює дані під час створення екземпляра
user = User(**user_data)

print(user.id)        # Вивід: 123 (тип int)
print(user.is_active) # Вивід: True (тип bool)
print(user.dict())
# Вивід: {'id': 123, 'name': 'Alex', 'is_active': True}

Якщо перетворення неможливе (наприклад, "id": "abc"), Pydantic згенерує виняток ValidationError.

Вкладені моделі та складні структури

Моделі Pydantic можуть містити інші моделі, а також стандартні типи колекцій Python, як-от list та dict. Це дозволяє описувати складні, вкладені структури даних.

Приклад:

from pydantic import BaseModel
from typing import List, Optional

class Author(BaseModel):
    id: int
    name: str

class Post(BaseModel):
    id: int
    title: str
    author: Author # <-- Вкладена модель
    tags: Optional[List[str]] = None # <-- Список рядків (опціональний)

Дані для валідації:

{
  "id": 1,
  "title": "FastAPI and Pydantic",
  "author": {
    "id": 101,
    "name": "Alice"
  },
  "tags": ["python", "api", "fastapi"]
}

Pydantic рекурсивно провалідує всю структуру: перевірить, що author відповідає моделі Author, а tags є списком рядків.

Інформативні повідомлення про помилки

Якщо дані не проходять валідацію, Pydantic генерує виняток ValidationError з дуже детальним описом усіх знайдених помилок. FastAPI автоматично перехоплює цей виняток і формує JSON-відповідь з кодом 422 Unprocessable Entity.

Приклад невалідних даних:

invalid_data = {
    "id": "abc", # Помилка: неможливо перетворити на int
    "name": 123,   # Помилка: очікується str
    # Поле is_active відсутнє, хоча воно є обов'язковим
}

Приклад відповіді від FastAPI:

{
  "detail": [
    {
      "loc": ["body", "id"],
      "msg": "value is not a valid integer",
      "type": "type_error.integer"
    },
    {
      "loc": ["body", "name"],
      "msg": "str type expected",
      "type": "type_error.str"
    },
    {
      "loc": ["body", "is_active"],
      "msg": "field required",
      "type": "value_error.missing"
    }
  ]
}

Ця детальна відповідь дуже допомагає фронтенд-розробникам та користувачам API зрозуміти, що саме потрібно виправити в запиті.

Використання Field для додаткової валідації

Для додавання жорсткіших обмежень до полів (окрім типу) використовується функція Field з Pydantic.

Імпорт: from pydantic import Field

Приклад:

from pydantic import BaseModel, Field, EmailStr
from typing import Optional

class Product(BaseModel):
    name: str = Field(
        ..., # ... означає, що поле є обов'язковим
        min_length=3,
        max_length=50,
        description="Назва товару (від 3 до 50 символів)"
    )
    price: float = Field(
        ...,
        gt=0, # gt (greater than) - більше ніж 0
        le=100000.0, # le (less than or equal) — менше або дорівнює 100000
        description="Ціна має бути в діапазоні (0, 100000]"
    )
    description: Optional[str] = Field(
        None,
        title="Опис",
        max_length=500
    )
    # Pydantic має спеціальні типи для валідації, наприклад, EmailStr
    contact_email: Optional[EmailStr] = None

Інші обмеження: lt (менше), ge (більше або дорівнює), regex, deprecated тощо.

Власні валідатори

Якщо вбудованих обмежень Field недостатньо, ви можете написати власні функції-валідатори за допомогою декоратора @field_validator.

Імпорт: from pydantic import field_validator

Приклад: перевірка, що назва товару не містить заборонених слів.

from pydantic import BaseModel, Field, field_validator

class Product(BaseModel):
    name: str = Field(..., min_length=3)
    price: float = Field(..., gt=0)

    # Валідатор для поля 'name'
    @field_validator('name')
    @classmethod # Валідатори Pydantic v2 є classmethod
    def validate_name_not_forbidden(cls, value: str) -> str:
        if "спам" in value.lower() or "реклама" in value.lower():
            raise ValueError("Назва не може містити заборонених слів.")
        # Завжди повертаємо валідне значення
        return value

Існує також декоратор @model_validator для валідації, що залежить від кількох полів (cross-field validation).

Валідація даних у запитах FastAPI

Як ви вже бачили, Pydantic-моделі використовуються для автоматичної валідації тіла POST, PUT, PATCH-запитів.

from fastapi import FastAPI
from pydantic import BaseModel, EmailStr

app = FastAPI()

class UserCreate(BaseModel):
    username: str
    email: EmailStr
    password: str

# FastAPI автоматично валідує тіло запиту за моделлю UserCreate
@app.post("/users/")
async def create_user(user: UserCreate):
    # Якщо код дійшов сюди, отже, дані в 'user' валідні
    # ... логіка створення користувача ...
    return {"username": user.username, "email": user.email}

Валідація Query та Path Parameters:
Для параметрів шляху та запиту Pydantic-моделі не використовуються безпосередньо, але FastAPI надає Path() та Query(), які використовують ті ж самі принципи валідації.

@app.get("/items/{item_id}")
async def get_item(
    item_id: int = Path(..., ge=1, description="ID товару"),
    query: str = Query(None, min_length=3, description="Рядок пошуку")
):
    return {"item_id": item_id, "query": query}

Валідація відповідей API (response_model)

Використання аргументу response_model у декораторі ендпоінта — це найкраща практика для забезпечення надійності вашого API.

Що робить response_model:

  • Фільтрує дані: гарантує, що відповідь API міститиме лише ті поля, що визначені в моделі response_model. Це запобігає випадковому розкриттю чутливих даних (наприклад, хешів паролів, внутрішніх полів).
  • Валідує дані: перевіряє, що типи даних у відповіді узгоджені з моделлю.
  • Документує відповідь: FastAPI використовує response_model для генерації точної схеми відповіді в Swagger/OpenAPI.

Приклад:

from pydantic import BaseModel

class UserInDB(BaseModel): # Модель, як у БД
    username: str
    email: str
    hashed_password: str

class UserOut(BaseModel): # Модель для відповіді API
    username: str
    email: str

@app.get("/users/{user_id}", response_model=UserOut)
async def get_user(user_id: int):
    # Припустимо, з БД ми отримали об'єкт з усіма полями
    user_db_data = UserInDB(
        username="alex",
        email="alex@example.com",
        hashed_password="supersecret"
    )
    # FastAPI автоматично відфільтрує відповідь згідно з UserOut,
    # і 'hashed_password' не потрапить у JSON.
    return user_db_data

Повний приклад CRUD-валідації

Поєднаємо всі концепції для API для керування подіями.

Моделі Pydantic:

from pydantic import BaseModel, Field, EmailStr
from datetime import date
from typing import List, Optional

class Participant(BaseModel):
    name: str = Field(..., min_length=2, max_length=50)
    email: EmailStr

class Event(BaseModel):
    id: int
    title: str = Field(..., min_length=5, max_length=100)
    date: date
    participants: List[Participant] = []

class EventUpdate(BaseModel): # Модель для оновлення (усі поля опціональні)
    title: Optional[str] = Field(None, min_length=5, max_length=100)
    date: Optional[date] = None
    participants: Optional[List[Participant]] = None

Ендпоінт для створення:

from fastapi import FastAPI, HTTPException

app = FastAPI()
events_db = {} # Імітація БД

@app.post("/events/", response_model=Event, status_code=201)
async def create_event(event_data: Event): # Валідація вхідних даних
    # Логіка присвоєння ID та збереження...
    events_db[event_data.id] = event_data
    return event_data # Валідація вихідних даних

Аналогічно створюються ендпоінти для GET, PUT (з EventUpdate) та DELETE.
