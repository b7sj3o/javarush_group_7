Рівень 4: Аутентифікація та авторизація з OAuth2 і JWT

Реалізація надійної автентифікації та авторизації з нуля — одна з найскладніших та потенційно вразливих частин будь-якого API. Ми заглибимося в сучасні стандарти OAuth2 та JWT, які пропонують перевірені рішення для цього завдання.

Ви дізнаєтеся, чому використання пари Access Token та Refresh Token підвищує безпеку, і як самодостатня природа JWT спрощує перевірку справжності запитів. Ми налаштуємо OAuth2PasswordBearer у FastAPI для автоматичного вилучення токенів, навчимося генерувати та перевіряти JWT за допомогою бібліотеки python-jose.

Буде розглянуто, як захищати ендпоінти та керувати доступом на основі ролей, що дозволить вам створювати надійні та stateless API.

Access Token та Refresh Token

OAuth2 — це відкритий стандарт авторизації, який дозволяє застосункам отримувати обмежений доступ до акаунтів користувачів на інших сервісах (наприклад, «Увійти через Google»), при цьому без отримання паролю користувача. Багато концепцій OAuth2, особливо використання токенів, лягли в основу сучасних систем аутентифікації в API.

У сучасних stateless API, включно з тими, що розроблені за принципами OAuth2, аутентифікація майже завжди базується на токенах.

Access Token:

  • це ключ, який клієнт (наприклад, фронтенд) пред'являє API під час кожного запиту для підтвердження своєї особистості та прав.
  • короткотривалий: зазвичай термін його дії становить від 5 до 60 хвилин.
  • передається в HTTP-заголовку Authorization.
  • формат: Authorization: Bearer <access_token>

Refresh Token:

  • це спеціальний ключ, єдине завдання якого — отримати новий Access Token, коли в старого минув термін придатності.
  • довготривалий: може діяти дні, тижні або місяці.
  • зберігається клієнтом більш безпечно і використовується рідко.

Навіщо два токени? Це підвищує безпеку. Якщо Access Token буде перехоплено, він швидко стане недійсним. Компрометація Refresh Token — більш рідкісна та серйозна подія, яку легше відстежити та заблокувати.

JSON Web Tokens

JWT (JSON Web Token) — це відкритий стандарт (RFC 7519) для створення компактних та самодостатніх токенів. Це не просто випадковий рядок, а закодований JSON-об'єкт.

Структура JWT (header.payload.signature):

  1. Header: метадані — тип токена (typ: "JWT") та алгоритм підпису (alg: "HS256").
  2. Payload: дані (заяви, claims) про користувача (наприклад, user_id, username, role) та метадані токена (наприклад, exp — час завершення терміну дії).
  3. Signature: створюється шляхом підпису header та payload з використанням секретного ключа, відомого лише серверу.

Підпис створюється з Header та Payload із використанням секретного ключа. Будь-яка зміна в header або payload зробить підпис невалідним.

Налаштування аутентифікації у FastAPI

FastAPI надає гнучкі інструменти для інтеграції схем безпеки, таких як OAuth2 з JWT.

Основний інструмент: OAuth2PasswordBearer.

  • імпорт: from fastapi.security import OAuth2PasswordBearer.
  • призначення: це клас-залежність, який "знає", як знайти токен у вхідному запиті. Він шукає заголовок Authorization і витягує з нього токен (значення після Bearer ).
  • використання: створюється екземпляр, якому передається URL ендпоінта для отримання токена. Це використовується для автоматичної документації (Swagger UI).
# main.py або auth.py
from fastapi import Depends, FastAPI
from fastapi.security import OAuth2PasswordBearer

app = FastAPI()

# Створюємо екземпляр схеми. 'token' — це URL, де клієнт може отримати токен.
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")

# Захищений ендпоінт
@app.get("/users/me")
async def read_users_me(token: str = Depends(oauth2_scheme)):
    # У змінній 'token' буде вміст токена, який витягнуто із заголовка.
    # Далі ми будемо його перевіряти.
    return {"token": token}

Тепер Swagger UI для ендпоінта /users/me матиме кнопку "Authorize", що дозволяє вставити токен для тестування.

Генерація та перевірка JWT-токенів

Примітка: замість ручної роботи з JWT на практиці часто використовують перевірені бібліотеки, такі як python-jose (рекомендована FastAPI) або PyJWT.

Встановлення python-jose:

pip install "python-jose[cryptography]"

Логіка створення та перевірки:

# auth.py
from jose import JWTError, jwt
from datetime import datetime, timedelta, timezone
from pydantic import BaseModel

# --- Налаштування ---
SECRET_KEY = "a_very_secret_key_should_be_in_env_variables" # Зберігати в .env!
ALGORITHM = "HS256"
ACCESS_TOKEN_EXPIRE_MINUTES = 30

# --- Функції ---
def create_access_token(data: dict):
    to_encode = data.copy()
    expire = datetime.now(timezone.utc) + timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)
    to_encode.update({"exp": expire})
    encoded_jwt = jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)
    return encoded_jwt

def decode_token(token: str):
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        return payload
    except JWTError:
        return None # Або згенерувати виняток
  • create_access_token: приймає словник з даними (наприклад, {'sub': username}), додає час життя (exp) та створює підписаний JWT.
  • decode_token: приймає токен, перевіряє його підпис та термін дії. Якщо все гаразд, повертає payload.

Захист ендпоінтів через JWT

Тепер об'єднаємо OAuth2PasswordBearer та логіку роботи з JWT для створення залежності, яка захищатиме ендпоінти та повертатиме поточного користувача.

Приклад (auth.py):

from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer
# ... (імпорти та функції create/decode_token з минулого слайда) ...

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")

async def get_current_user(token: str = Depends(oauth2_scheme)):
    credentials_exception = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Could not validate credentials",
        headers={"WWW-Authenticate": "Bearer"},
    )
    payload = decode_token(token)
    if payload is None:
        raise credentials_exception
    username: str = payload.get("sub")
    if username is None:
        raise credentials_exception
    # Тут можна додати запит до БД для отримання об'єкта User за username
    # user = get_user_from_db(username=username)
    # if user is None: raise credentials_exception
    return {"username": username} # Повертаємо дані користувача з токена

Використання в ендпоінті:

# main.py
from . import auth

@app.get("/users/profile/me")
async def read_my_profile(current_user: dict = Depends(auth.get_current_user)):
    # Якщо код дійшов сюди, це означає, що токен валідний.
    # У current_user знаходяться дані з payload токена.
    return current_user

Приклад: ендпоінт для входу (отримання токена)

Щоб система запрацювала, потрібен ендпоінт, де користувач може обміняти свій логін та пароль на токен.

Форма для запиту токена:
FastAPI надає OAuth2PasswordRequestForm для зручності. Вона вимагає username та password.

# main.py
from fastapi import Depends, FastAPI, HTTPException
from fastapi.security import OAuth2PasswordRequestForm
from datetime import timedelta
from . import auth # Імпортуємо наш модуль auth

app = FastAPI()

@app.post("/token")
async def login_for_access_token(form_data: OAuth2PasswordRequestForm = Depends()):
    # Тут має бути перевірка користувача в БД
    # user = authenticate_user(form_data.username, form_data.password)
    # Для прикладу вважаємо, що пароль вірний, якщо він не порожній
    if not form_data.password: # Імітація перевірки
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Incorrect username or password",
        )
    # Створюємо токен для користувача
    access_token = auth.create_access_token(
        data={"sub": form_data.username, "roles": ["user"]} # "sub" — стандартне ім'я для суб'єкта
    )
    return {"access_token": access_token, "token_type": "bearer"}

Тепер клієнт може надіслати POST-запит на /token з username та password і отримати у відповідь JWT.

Обмеження доступу за ролями

Часто потрібно обмежити доступ до ендпоінтів на основі ролі користувача (наприклад, "admin", "manager", "user"). Інформацію про роль можна зберігати в payload JWT-токена.

Створення залежності для перевірки ролі:

# auth.py (продовження)
def require_role(required_role: str):
    async def role_checker(current_user: dict = Depends(get_current_user)):
        roles = current_user.get("roles", [])
        if required_role not in roles:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="You do not have permission to access this resource"
            )
        return current_user
    return Depends(role_checker)

Використання в ендпоінті:

# main.py
from . import auth

# Цей ендпоінт доступний лише користувачам з роллю 'admin' у токені
@app.get("/admin/dashboard")
async def get_admin_dashboard(admin_user: dict = auth.require_role("admin")):
    return {"message": f"Welcome to the admin dashboard, {admin_user['username']}!"}

# Цей ендпоінт доступний користувачам з роллю 'user'
@app.get("/user/data")
async def get_user_data(user: dict = auth.require_role("user")):
    return {"data": "some user-specific data"}

Цей підхід дозволяє створювати гнучку систему авторизації на основі ролей.
