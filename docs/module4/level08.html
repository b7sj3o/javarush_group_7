Рівень 8: NoSQL та MongoDB

Реляційні бази даних не завжди є оптимальним вибором, коли йдеться про швидкозмінні, неструктуровані або дуже великі обсяги даних, що потребують горизонтального масштабування. Ми зануримося у світ NoSQL, сфокусувавшись на MongoDB — провідній документоорієнтованій базі даних.

Ви дізнаєтеся її ключові відмінності від традиційних SQL-баз, зрозумієте, коли гнучка схема та денормалізація стають перевагою, а також познайомитеся з основними концепціями, такими як документи та колекції. Ми налаштуємо асинхронне підключення MongoDB до FastAPI за допомогою офіційного драйвера motor, навчимося виконувати всі CRUD-операції, створювати індекси для оптимізації запитів та використовувати мультидокументні ACID-транзакції, які відкривають нові можливості для роботи з NoSQL.

Що таке NoSQL?

NoSQL — це не "анти-SQL", а радше "Not Only SQL" (Не тільки SQL). Це загальна назва для баз даних, які не використовують класичну реляційну модель з таблицями та строгими схемами.

Ключові відмінності від SQL:

  • гнучка схема: ви можете додавати документи з різною структурою до однієї колекції. Немає потреби в ALTER TABLE для додавання нового поля.
  • масштабованість: NoSQL бази даних зазвичай простіше масштабувати горизонтально (додаючи більше серверів), ніж SQL бази (де зазвичай збільшують потужність одного сервера).
  • різні моделі даних: дані можуть зберігатися не лише в таблицях, а й у вигляді документів (JSON/BSON), пар ключ-значення, графів або колонок.

Типи NoSQL баз даних:

  • документоорієнтовані (MongoDB): наш фокус на цьому рівні.
  • ключ-значення (Redis): ідеально для кешування.
  • графові (Neo4j): для аналізу зв'язків (соцмережі, рекомендації).
  • колонкові (Cassandra): для великих обсягів запису (Big Data).

Коли обирати NoSQL?

Вибір між SQL та NoSQL залежить від завдання. NoSQL є особливо корисним, коли:

  • структура даних не до кінця визначена або часто змінюється: ідеально для стартапів, MVP та проєктів зі швидкою еволюцією.
  • потрібна висока продуктивність на запис та читання: наприклад, для систем логування, аналітики, IoT.
  • потрібна висока доступність та горизонтальне масштабування: для високонавантажених систем, які мають витримувати великий трафік.
  • дані мають природну ієрархічну або графову структуру: наприклад, профілі користувачів із вкладеними даними, соціальні зв'язки.

Не варто обирати NoSQL, якщо:

  • вам потрібні складні транзакції та 100% гарантія цілісності даних (ACID), як у банківських системах (хоча сучасні NoSQL, включно з MongoDB, вже підтримують транзакції).
  • усі ваші дані дуже структуровані та рідко змінюються.

Основні концепції MongoDB

MongoDB — це документоорієнтована NoSQL база даних.

  • Document: основна одиниця даних. Це BSON-об'єкт (бінарний JSON), що дуже схожий на словник Python або об'єкт JSON.
  • Collection: група документів. Це аналог таблиці в SQL, але без строгої схеми.
  • _id: унікальний ідентифікатор для кожного документа в колекції. Якщо ви не вказуєте його самі, MongoDB згенерує його автоматично (типу ObjectId). У JSON-поданні _id зазвичай відображається як рядок.
  • Денормалізація: у MongoDB прийнято зберігати пов'язані дані всередині одного документа (embedding), а не розносити їх різними таблицями і використовувати JOIN, як у SQL. Це прискорює читання, але може ускладнити оновлення.

Приклад документа в колекції users:

{
  "_id": "64a5f2b3e8c1d2e3f4a5b6c7",
  "username": "alex",
  "email": "alex@example.com",
  "is_active": true,
  "roles": ["editor", "user"],
  "profile": {
    "location": "New York",
    "bio": "Software developer."
  }
}

Зверніть увагу, що _id тут поданий як рядок, як це зазвичай буває при серіалізації для API.

Встановлення та підключення до MongoDB

Варіанти встановлення:

  • Docker:

    docker run --name my-mongo -d -p 27017:27017 mongo
  • MongoDB Atlas: хмарна версія MongoDB, ідеальна для продакшену, не вимагає ручного налаштування.
  • Локальна установка: завантажити та встановити MongoDB Community Server з офіційного сайту.

Connection String:
Формат: mongodb://[username:password@]host[:port]/[database]

  • локально: mongodb://localhost:27017
  • з автентифікацією: mongodb://user:password@localhost:27017
  • в Atlas: ви отримаєте рядок підключення в інтерфейсі Atlas.

Перевірка роботи через mongosh (CLI):

# Підключитися до локального сервера
mongosh

# Переключитися на базу (створиться при першому записі)
use myFastApiDb

# Вставити документ
db.users.insertOne({ name: "Alice", age: 30 })

# Знайти документ
db.users.find({ name: "Alice" })

FastAPI + MongoDB: асинхронне підключення

Для асинхронної роботи з MongoDB з FastAPI використовується бібліотека motor. Це офіційний асинхронний драйвер від розробників MongoDB.

Встановлення:

pip install motor
pip freeze > requirements.txt

Налаштування підключення (database.py):

from motor.motor_asyncio import AsyncIOMotorClient, AsyncIOMotorDatabase

# --- Налаштування ---
MONGO_DETAILS = "mongodb://localhost:27017"
DB_NAME = "myFastApiDb"

# --- Клієнт та підключення ---
client = AsyncIOMotorClient(MONGO_DETAILS)
database = client[DB_NAME] # Отримуємо об'єкт бази даних

# Функція для отримання об'єкта бази даних (можна використовувати як залежність)
def get_database() -> AsyncIOMotorDatabase:
    return database

Використання в ендпоінті:

from fastapi import FastAPI, Depends

app = FastAPI()
users_collection = database.get_collection("users") # Отримуємо об'єкт колекції

@app.get("/users/me")
async def get_my_user():
    # await — оскільки всі операції motor є асинхронними
    user_data = await users_collection.find_one({"username": "alex"})
    # Потрібно обробити _id, оскільки він не серіалізується в JSON за замовчуванням
    if user_data:
        user_data["_id"] = str(user_data["_id"])
    return user_data

CRUD-операції в MongoDB з motor

Усі операції з motor асинхронні та вимагають await.

Create:

# insert_one: вставити один документ
new_user = {"name": "Bob", "age": 25}
result = await collection.insert_one(new_user)
print(f"Вставлено документ з id: {result.inserted_id}")

# insert_many: вставити список документів
# await collection.insert_many([user1, user2])

Read:

# find_one: знайти перший документ, що відповідає фільтру
user = await collection.find_one({"name": "Bob"})

# find: знайти всі документи, що відповідають фільтру (повертає курсор)
async for doc in collection.find({"age": {"$gt": 20}}): # $gt -> greater than
    print(doc)

Update:

# update_one: оновити перший знайдений документ
await collection.update_one(
    {"name": "Bob"}, # Фільтр для пошуку документа
    {"$set": {"age": 26, "is_active": True}} # Оператор $set для оновлення полів
)
# update_many: оновити всі знайдені документи

Delete:

# delete_one: видалити перший знайдений документ
await collection.delete_one({"name": "Bob"})
# delete_many: видалити всі знайдені документи

Робота з колекціями та індексами

У MongoDB колекція та база даних створюються автоматично під час першого вставлення документа. Немає необхідності виконувати CREATE TABLE.

Індекси:

  • як і в SQL, індекси критично важливі для продуктивності операцій читання. Без індексів MongoDB скануватиме всю колекцію (full collection scan) для пошуку документів.
  • MongoDB автоматично створює індекс для поля _id.
  • ви повинні створювати індекси для полів, за якими часто виконуєте пошук, фільтрацію або сортування.

Створення індексу з motor:

# Створити унікальний індекс за полем 'email' у фоновому режимі
await collection.create_index("email", unique=True, background=True)

# Створити складений індекс (за кількома полями)
# 1 — за зростанням, -1 — за спаданням
await collection.create_index([("name", 1), ("age", -1)], background=True)

Індекси створюються один раз, а потім використовуються базою даних автоматично.

Транзакції в MongoDB

З версії 4.0 MongoDB підтримує мультидокументні ACID-транзакції, що дозволяє виконувати кілька операцій як єдину атомарну дію.

Коли це потрібно:

  • коли вам потрібно гарантувати те, що або всі операції запису (в одну чи кілька колекцій) будуть успішними, або жодна з них не буде застосована.
  • приклад: банківський переказ (списання з одного рахунку та зарахування на інший).

Використання з motor:
Транзакції виконуються в межах сесії.

async with await client.start_session() as session:
    # Починаємо транзакцію
    async with session.start_transaction():
        try:
            # Виконуємо операції всередині транзакції, передаючи сесію
            await accounts_collection.update_one(
                {"_id": account_a_id},
                {"$inc": {"balance": -100}},
                session=session
            )
            await accounts_collection.update_one(
                {"_id": account_b_id},
                {"$inc": {"balance": 100}},
                session=session
            )
            # Якщо дійшли сюди без помилок, транзакція буде автоматично підтверджена (commit)
        except Exception:
            # Якщо сталася помилка, транзакція буде автоматично скасована (abort)
            print("Транзакцію скасовано.")
            raise

Важливо! Для використання транзакцій ваш сервер MongoDB має бути розгорнутий як Replica Set.

Приклад простого API (To-Do List)

Об'єднаємо FastAPI, Pydantic та Motor для створення простого CRUD API.

Моделі Pydantic (models.py):

from pydantic import BaseModel, Field
from typing import Optional

class Todo(BaseModel):
    id: Optional[str] = Field(alias="_id", default=None) # Мапінг _id на id
    title: str
    description: Optional[str] = None
    is_completed: bool = False

class TodoUpdate(BaseModel):
    title: Optional[str] = None
    description: Optional[str] = None
    is_completed: Optional[bool] = None

Ендпоінт створення (routes.py):

from fastapi import APIRouter, Body, status
from .models import Todo

router = APIRouter()
# Припускаємо, що 'todo_collection' імпортовано з database.py

@router.post("/", response_model=Todo, status_code=status.HTTP_201_CREATED)
async def create_todo(todo: Todo = Body(...)):
    # Перетворюємо Pydantic модель на словник
    new_todo = await todo_collection.insert_one(todo.model_dump(by_alias=True, exclude=["id"]))
    created_todo = await todo_collection.find_one({"_id": new_todo.inserted_id})
    return created_todo

model_dump() (в Pydantic v2) використовується для перетворення моделі на словник. by_alias=True гарантує, що поле id стане _id.

SQL JOIN vs MongoDB Embedding

У SQL для отримання пов'язаних даних потрібні JOIN. У MongoDB часто всі необхідні дані зберігаються в одному вкладеному документі, що прискорює читання.

graph LR subgraph SQL JOIN direction LR U[Users] -- one-to-many --> O[Orders]; O -- many-to-many --> P[Products]; subgraph Запит Q1("SELECT ... FROM Users JOIN Orders ... JOIN Products ...") end end subgraph MongoDB Embedding direction LR DU[User Document] --> DO{"orders: [...]"}; subgraph "Вкладене замовлення" DO --> DOP{"products: [...]"}; end subgraph Запит Q2("db.users.findOne({_id: ...})") end end

Оптимізація запитів у MongoDB

  • Індекси: найважливіший інструмент оптимізації. Створюйте індекси на всіх полях, за якими ви фільтруєте, сортуєте або шукаєте.
  • Денормалізація (Embedding): зберігайте дані, які часто читаються разом, в одному документі, щоб уникнути додаткових запитів. Але не зловживайте, якщо дані часто оновлюються окремо.

  • Проєкція (Projection): робіть запит лише на ті поля, які вам потрібні, а не на весь документ. Це зменшує навантаження на мережу та сервер.

    # Повернути тільки поля 'name' та 'email', виключаючи '_id'
await collection.find_one({"_id": user_id}, {"_id": 0, "name": 1, "email": 1})

  • Використання explain(): аналізуйте план виконання ваших запитів, щоб переконатися, що вони використовують індекси, а не сканують всю колекцію.

    explain_plan = await collection.find({"username": "alex"}).explain()
# Вивчіть explain_plan['queryPlanner']['winningPlan']
